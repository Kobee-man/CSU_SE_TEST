整理日期：2026-10-23。依据：[REA 完整分析报告](REA分析/完整分析报告.md)、[源码审查](REA分析/源码审查.md)、[补充项目与工程化审查](REA分析/补充项目与工程化审查.md)。

本文汇总 **24 项问题：P1 六项、P2 十六项、P3 两项**，供修复分工和验收使用。P1 优先处理数据、安全和关键入口；P2 处理稳定性、兼容性与工程交付；P3 为局部资源和展示问题。优先级为项目建议，不是漏洞评分。

原始清单编写时所有问题均为**待处理**。“静态确认”表示源码或 APK 中已确认相应实现；“待运行验证”表示影响仍需要在设备、数据库或网络条件下复现。原始分析没有执行 APK，不能把静态问题清单当作实测故障记录。

**2026-10-23 修复进展：** 已修改维护中的中文版、SmartTodo 和预览工具，补充业务测试并生成新版交付。各项实际状态、已执行验证与仍需云端／人工验收的条件见 [问题修复与验收记录](问题修复与验收记录.md)；不要再以本清单原始“待处理”状态代表最新进展。

## 二、P1：优先处理

### Q01｜SmartTodo 的 API 凭据已进入 APK

- **现象与证据**：`baidu/com/Sample.java` 中硬编码两项凭据；已确认两个字面量均存在于 APK DEX。见[脱敏检查记录](REA分析/证据/supplement-source-package-audit.json)。
- **影响**：持有 APK 的人可提取上游鉴权材料。凭据是否仍有效、是否已被滥用未联网验证。
- **修复要求**：轮换或撤销现有凭据；需要保密的上游鉴权移到服务端，客户端使用受控会话。仅改成资源文件或增加混淆不能解决随包分发的问题。
- **验收标准**：新 APK 不含旧密钥或长期上游秘密；旧凭据失效；服务端具备鉴权、限流与额度控制。文档和日志继续脱敏。

### Q02｜便签保存失败可能仍被上层报告为成功

- **现象与证据**：`WorkingNote.saveNote()` 忽略 `Note.syncNote()` 的返回值，随后返回 true；note 更新影响零行时也只是记录日志。交付 APK 已确认，见[保存方法](REA分析/证据/delivered-method-model.WorkingNote.saveNote.json)。
- **影响**：界面及生命周期保存无法可靠识别失败，草稿恢复可能依赖未成功完成的写入。
- **修复要求**：统一保存结果语义，传播真实错误并保留草稿；同时修正“新 data 插入成功但未形成 batch 时返回 null”的结果歧义，不能只机械透传现有返回值。
- **验收标准**：成功保存可重载；更新零行、Provider 失败等场景明确报错，不出现虚假成功，用户仍可重试。

### Q03｜便签跨表保存缺少事务保障，提交前清空差异数据

- **现象与证据**：note/data 分步写入；NoteData 在后续 batch 完成前清空差异值；Provider 未覆盖完整业务事务。源码与交付 APK 均有支持，见[NoteData 写入方法](REA分析/证据/delivered-detail-net.micode.notes.model.Note.NoteData.pushIntoContentResolver0.json)。
- **影响**：中途失败可能留下部分保存状态，且原始差异不足以原样重试。静态分析没有证明真实用户已发生数据丢失。
- **修复要求**：将整次相关写入纳入同一 SQLite 事务，逐项检查结果；确认提交成功后再清空工作差异。
- **验收标准**：任一写入步骤注入失败后数据库保持一致，失败草稿可重试；正常保存与批量更新均通过重载核对。

### Q04｜SmartTodo 的一个桌面启动入口指向不存在的类

- **现象与证据**：APK 声明两个 MAIN/LAUNCHER，其中 `com.example.emptyactivity.MainActivity` 在全部六个 DEX 的类定义中不存在；`FirstActivity` 存在。见[APK 清单](REA分析/证据/smarttodo-package.json)及[类检查](REA分析/证据/supplement-source-package-audit.json)。
- **影响**：按普通 Android 类加载流程，该入口无法正常启动；本轮未点击图标取得崩溃日志，不能说全部入口均失败。
- **修复要求**：明确产品首页，只保留正确入口，统一 Manifest 与 Activity 全限定类名。
- **验收标准**：安装后出现预期数量的图标；桌面点击、显式启动和冷启动均进入正确页面，无缺失 Activity 错误。

### Q05｜SmartTodo 待办数据没有持久化与重建恢复

- **现象与证据**：新增、完成、删除仅操作动态 View；限定全部八个 Java 文件，未找到待办仓储或持久化路径。见[补充审查第 2.3 节](REA分析/补充项目与工程化审查.md#23-p1待办事项没有持久化或重建恢复)。
- **影响**：当前实现无法在进程退出、Activity 重建后恢复待办内容和完成状态，AI 建议也没有持久化写回链路。
- **修复要求**：定义稳定 ID、内容、完成状态等模型，用 Room/SQLite 等持久化，并由数据驱动界面。
- **验收标准**：新增、完成、删除后，旋转、退出重进及进程重建都能恢复一致数据；不同待办之间不串状态。

### Q06｜同步服务重建存在 null Intent 异常路径

- **现象与证据**：`GTaskSyncService.onStartCommand()` 先执行 `intent.getExtras()`，部分分支返回 START_STICKY；系统重建服务时允许传入 null。交付 APK 已确认，见[服务方法](REA分析/证据/delivered-method-gtask.remote.GTaskSyncService.onStartCommand.json)。
- **影响**：服务被系统重新创建时可能空指针崩溃；这是生命周期路径，不是已证明的外部服务调用漏洞。
- **修复要求**：增加空值保护，明确重建后的任务恢复策略，并重新评估是否需要 START_STICKY。
- **验收标准**：直接以 null 调用该入口及模拟系统重建均安全；续传或退出行为符合约定，不产生重复同步任务。

## 六、不应误写成缺陷的结论

- JADX 已可用，不再列为当前安装阻塞。
- 没有证据证明 NotesProvider 对外公开全部便签，也没有建立任意外部 SQL 注入链。
- OkHttp `ResponseBody.string()` 正常读取会关闭响应体，不能只因未写 response.close 就判定正常路径泄漏。
- 没有运行证据证明普通语言切换必然丢字；风险在保存失败与异常生命周期，需要定向验证。
- 交付 APK 含九个 DEX；Notesmaster 同源关系和 SmartTodo 独立实现均已区分，不能混称为一个完成 AI 集成的产品。
